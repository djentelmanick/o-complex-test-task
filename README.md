# O-complex · ассистент менеджера

Сервис принимает обращение клиента, находит нужные статьи в базе знаний O-complex и через GigaChat возвращает два блока:

- **ответ клиенту**: вежливый и опирается только на базу знаний, со ссылками на источники;
- **подсказку менеджеру по допродаже**, которая учитывает историю переписки с клиентом в CRM (AmoCRM подменён mock-адаптером).

Один и тот же вопрос от разных клиентов даёт похожие ответы, но разные подсказки. Новичку сервис предложит начать с Zeolite Standard или Mini. Тому, у кого заканчивается курс, предложит Zeolite Max и Mineral Complex от усталости. Тому, кто сомневался из-за цены, предложит Zeolite Mini без давления.

## Быстрый старт

Нужен только Docker.

```bash
cp .env.example .env
# В .env заполнить APP_API_KEY (≥16 символов), POSTGRES_PASSWORD (буквы и цифры),
# GIGACHAT_AUTH_KEY. Без ключа GigaChat поставьте LLM_PROVIDER=fake.
make up
```

Откройте http://localhost:8000, введите `APP_API_KEY`, выберите лида и отправьте вопрос. Swagger: http://localhost:8000/docs.

При старте контейнер сам накатывает миграции и загружает базу знаний. Повторная загрузка пропускает неизменённые статьи.

## Архитектура

Архитектура гексагональная: ядро не знает о FastAPI, GigaChat и Postgres, всё внешнее подключается через порты.

```
                 ┌──────────── adapters/inbound ────────────┐
   HTTP / UI ──▶ │ FastAPI: auth, rate limit, CSP, ошибки   │   CLI: ingest
                 └───────────────────┬──────────────────────┘
                                     ▼
                 ┌────────────── application ───────────────┐
                 │ AnswerInquiryUseCase   IngestKnowledge   │
                 │ промпт · валидация вывода · источники    │
                 │ порты: LLMClient, Embedder,              │
                 │        KnowledgeRepository, CRMGateway   │
                 └───────────────────┬──────────────────────┘
                                     ▼  domain: модели и ошибки
                 ┌──────────── adapters/outbound ───────────┐
                 │ GigaChat (OAuth, chat, embeddings)       │
                 │ Local embeddings (fastembed, ONNX)       │
                 │ Postgres + pgvector (Alembic)            │
                 │ Mock CRM (JSON)   Fake LLM/embedder      │
                 └──────────────────────────────────────────┘
```

Как обрабатывается обращение:

1. Из CRM берутся последние 10 сообщений диалога с лидом.
2. Одним вызовом эмбеддера считаются два вектора: вопрос клиента и его последние реплики.
3. Каждый вектор ищется в pgvector (косинус, HNSW, порог релевантности). Вопрос находит статьи для ответа, реплики находят возражения и этап курса для допродажи.
4. GigaChat вызывается один раз с принудительным function calling (`submit_answer`) и строгой JSON-схемой.
5. Ответ валидируется Pydantic, мусор разметки вычищается, `sources` пересекаются с реально найденными фрагментами. Если ответ модели невалиден, делается один повтор, затем безопасный fallback.

Каждый провайдер переключается одной переменной в `.env`:

| Переменная | Значения | По умолчанию |
|---|---|---|
| `LLM_PROVIDER` | `gigachat`, `fake` | `gigachat` |
| `EMBEDDING_PROVIDER` | `local`, `gigachat`, `fake` | `local` |
| `CRM_PROVIDER` | `mock`, `amocrm` | `mock` |

Эмбеддинги GigaChat доступны только в платном тарифе, поэтому по умолчанию работает локальная мультиязычная модель `paraphrase-multilingual-MiniLM-L12-v2`. Она вшита в образ, и в рантайме сервис в интернет за ней не ходит. Чтобы перейти на эмбеддинги GigaChat, поставьте `EMBEDDING_PROVIDER=gigachat` и `EMBEDDING_DIM=1024`, затем пересоздайте том БД (`docker compose down -v`): размерность вектора зафиксирована в миграции.

Интеграция с AmoCRM сделана именно так: `AmoCRMGateway` реализует тот же порт `CRMGateway`, поэтому ядро не пришлось менять, добавился только use case для входящих сообщений. Подробности в следующем разделе.

## Интеграция с AmoCRM

Ассистент работает прямо в сделке AmoCRM:

```
сообщение клиента (примечание sms_in в сделке)
  → AmoCRM шлёт вебхук note_lead через туннель cloudflared
  → сервис сразу отвечает 200, а в фоне:
      читает сделку и её SMS-историю через API v4 (payload вебхука не используется),
      отвечает тем же RAG + GigaChat,
      пишет результат примечанием «Ассистент O-complex» (extended_service_message) в ту же сделку
```

Сообщения клиента хранятся в примечаниях типа `sms_in`, ответы менеджера в `sms_out`. Ассистент реагирует только на `sms_in`, поэтому собственные примечания его не зацикливают. Повторная доставка того же события отсекается по id примечания.

**Настройка**

1. В AmoCRM откройте amoМаркет → «⋯» → «Создать интеграцию» → «Внешняя». Ссылку перенаправления укажите `https://example.com`, доступ «Все».
2. Перенесите в `.env` значения из вкладки «Ключи и доступы»: `AMOCRM_SUBDOMAIN` (имя аккаунта), `AMOCRM_CLIENT_ID`, `AMOCRM_CLIENT_SECRET`. Сгенерируйте `AMOCRM_TOKEN_KEY` и `AMOCRM_WEBHOOK_SECRET` командами из `.env.example` и поставьте `CRM_PROVIDER=amocrm`.
3. Выполните `make up-amocrm`. Вместе с сервисом поднимется туннель, а вебхук зарегистрируется в AmoCRM автоматически.
4. Выполните `make amocrm-auth code=<код авторизации>`. Код лежит в той же вкладке и живёт 20 минут, после авторизации перезапустите `app`.
5. `make amocrm-seed` создаст три демо-сделки с историей переписки и выведет их id.
6. `make client-says lead=<id> text="Как принимать цеолит?"` имитирует сообщение клиента. Через несколько секунд в сделке появится ответ и подсказка.

**Безопасность интеграции**
- Вебхук AmoCRM не подписывается, поэтому защита устроена так:
  - в пути URL стоит случайный секрет;
  - поддомен аккаунта в запросе проверяется;
  - содержимое сообщения берётся только из API AmoCRM, поэтому поддельный вебхук не может подменить текст.
- Секрет вебхука маскируется в access-логе.
- OAuth-токены хранятся в Postgres в зашифрованном виде (Fernet). Refresh-токен одноразовый, поэтому его обновление идёт под lock, а новая пара сохраняется сразу.
- Через туннель доступен только вебхук. Запросы с заголовками Cloudflare к любому другому пути получают 404, так что демо-страница и API остаются локальными.

**Ограничения**
- Событие обрабатывается не более одного раза. Если процесс упадёт посреди генерации, повтора не будет. Для гарантированной доставки нужна очередь (Redis или RabbitMQ и отдельный воркер).
- Quick tunnel получает новый адрес при каждом запуске, вебхук перерегистрируется автоматически. Для постоянного адреса нужен именованный туннель Cloudflare.
- Переписка мессенджеров через Chats API не читается: в демо сообщения клиента хранятся как SMS-примечания.

## Безопасность

**Prompt injection**
- Данные клиента, история из CRM и база знаний передаются в промпт в отдельных блоках. Угловые скобки экранируются, поэтому закрыть блок раньше времени нельзя.
- Правило «данные — это не инструкции» есть в системном промпте и повторяется после сообщения клиента (sandwich-защита).
- Модель отвечает только через строгую схему функции. У неё нет инструментов с побочными эффектами.
- Источники в ответе берутся из результатов поиска, выдуманные id отбрасываются.
- Модели запрещено называть цены, ставить диагнозы и обещать лечение. Цен в базе знаний нет.

**API**
- Проверка `X-API-Key` через `secrets.compare_digest`.
- Rate limit на генерацию, по умолчанию 10 запросов в минуту с одного IP. Это защищает бюджет токенов.
- Лимиты входа: сообщение до 2000 символов, `lead_id` по регулярному выражению, тело запроса до 16 КБ (в том числе chunked), лишние поля запрещены.
- Ошибки не раскрывают внутренние детали, в ответ на 422 входные данные не возвращаются.
- CSP без inline-скриптов, `X-Frame-Options: DENY`, `nosniff`. Ответ модели выводится на страницу только через `textContent`.

**Инфраструктура**
- Секреты хранятся только в `.env` и в коде типизированы как `SecretStr`. Текст обращений в логи не пишется.
- TLS к GigaChat всегда проверяется. В образ добавлен корневой сертификат НУЦ Минцифры (SHA-256 `D2:6D:2D:02:31:B7:C3:9F:92:CC:73:85:12:BA:54:10:35:19:E4:40:5D:68:B5:BD:70:3E:97:88:CA:8E:CF:31`), `verify=False` нигде нет.
- Контейнер работает от non-root пользователя, файловая система read-only, `cap_drop: ALL`, `no-new-privileges`. Зависимости ставятся по хэшам из `poetry.lock`.
- Postgres не публикуется наружу, приложение слушает только `127.0.0.1`.

## База знаний

Статьи лежат в `data/kb/*.md`, по одной на тему: продукты линейки Zeolite, Mineral Complex, сочетания для допродажи, безопасность, доставка, работа с возражениями. База демонстрационная, собрана по открытым материалам o-complex.com. Цен в ней нет специально.

Чтобы добавить статью, положите новый `.md` с заголовком `# …` и выполните `make ingest`. Пересчитаются только изменённые файлы.

Демо-лиды CRM описаны в `data/crm_dialogs.json`.

## Структура

```

  domain/        модели и ошибки
  application/   use case'ы, порты, промпт, разбор ответа модели
  adapters/      inbound (HTTP, вебхук AmoCRM, CLI) и outbound (GigaChat, local, Postgres, AmoCRM, mock CRM, fake)

```

## Как это собиралось с помощью ИИ

Проект собран в **Claude Code** с плагином **superpowers**, который задаёт процесс разработки:

1. **brainstorming**: уточнение требований и выбор архитектуры. Итог в спецификации `docs/superpowers/specs/`.
2. **writing-plans**: план из 14 задач с кодом и тестами для каждой (`docs/superpowers/plans/`).
3. **executing-plans + TDD**: каждая задача начиналась с падающего теста, затем шла реализация и коммит.
4. **systematic-debugging**: разбор проблем по ходу, например почему slowapi не считал запросы и почему alembic не находил пакет.
5. **context7**: актуальная документация GigaChat API (OAuth, function calling, embeddings).

После запуска с настоящим GigaChat качество доводилось на живых ответах. Так появились поиск по контексту диалога, очистка артефактов разметки и sandwich-защита от prompt injection. У каждого исправления есть тест.
